# Разобрать жалобы

Жалобы приходят с телефона сами и лежат в issues репозитория
`voronkovlabs/android-russian-montenegrin` с меткой **жалоба**. Задача скилла —
не пересказать их, а **починить и закрыть**.

`gh` установлен машинно и в PATH оболочки попадает не всегда:
`export PATH="$PATH:/c/Program Files/GitHub CLI"`.

## 1. Собрать

```
gh issue list --label "жалоба" --state open --limit 100 --json number,title,body,labels,createdAt
```

Метка кириллическая — в кавычках она работает, проверено.

У каждой issue внизу свёрнутый блок `Запись целиком` с исходной строкой JSONL.
**Разбирай его, а не размеченный текст:** в тексте пустые поля выброшены и всё
перемешано с подписями, а строка читается `json.loads` целиком.

```python
m = re.search(r'```json\n(.*?)\n```', body, re.S)
```

У жалоб, пришедших до 1.47, блока нет — там придётся читать размеченные поля.

## 2. Отсеять уже починенное

**Первым делом сверь `versionCode` записи с нынешним** (`src/app/build.gradle.kts`).
Половина жалоб приходит на то, что уже исправлено: очередь на телефоне копилась
неделями, а issue завелась сегодня. Такие закрывай с указанием версии, в которой
починено, и **не переделывай.**

Проверяй по коду и по `STATUS.md`, а не по памяти: «кажется, я это чинил» —
не основание.

## 3. Разобрать по существу

Категория говорит, где чинить, — она для этого и заведена:

| метка | где чинить |
|---|---|
| Claude ошибся | системный промпт в `net/HaikuChecker.kt`, **не логика приложения** |
| эталон неверен, и так верно, опечатка | JSON урока в `assets/lessons/` — строка ищется по `exerciseId` |
| плохо слышно | само задание: текст, скорость, разбивка |
| заметка, другое | что угодно; смысл в тексте |

**Ищи причину глубже жалобы.** Владелец описывает, что видит, а не что сломано.
Пример из 1.43: жаловались, что собранная фраза рассыпается после проверки, — а
причиной оказалось, что `ExerciseBody` вызывался внутри каждой ветки
`when (phase)`, то есть тело задания пересоздавалось при смене фазы. Починка
одного места заодно вылечила исчезавший текст и пары, которые показывались
несложенными; о них никто не жаловался.

**Несколько жалоб на одно и то же — одна починка.** Закрывай все, ссылаясь на
ту, где разобрано подробнее.

**Не всё чинится кодом.** Если жалоба — просьба поменять решение проекта
(«история должна начинаться сначала»), сперва скажи владельцу, чем это грозит, и
только потом делай. Молча менять записанное решение нельзя, молча
игнорировать — тоже.

## 4. Починить и проверить

Правь код и уроки как обычно; после каждой правки —
`cd src && ./gradlew :app:compileDebugKotlin`.

Содержательные правки проверяй прогоном по всем заданиям, а не на одном
примере: в курсе 374 задания, и правило, верное для одного, часто ломает
соседнее.

## 5. Закрыть issue

Каждую починенную — с комментарием о том, **что именно сделано** и в какой
версии:

```
gh issue close 12 --comment "Починено в 1.43: ..."
```

**Не чинишь — закрывай как `not planned`:**

```
gh issue close 12 --reason "not planned" --comment "Посмотрел, чинить нечего: ..."
```

Это не формальность. С 1.79 приложение само показывает человеку уведомление
«твою жалобу разобрали», и отличает оно починенное от непочиненного ровно по
`state_reason`. Закрытая по умолчанию issue считается выполненной, то есть
закрытая без правки соврёт человеку, что его услышали и сделали.

Правила закрытия:

* закрывай **только то, что действительно починил**. Непочиненное оставляй
  открытым и скажи владельцу, почему;
* то, что решает владелец, не закрывай вовсе — спроси;
* комментарий пишется для будущего себя: через месяц «исправлено» без
  подробностей не скажет ничего.

## 6. Довести до конца

Как всегда в этом проекте: поднять версию, обновить `CLAUDE.md` (если менялось
устройство) и `STATUS.md` (разбор жалоб — отдельным разделом с датой), собрать
APK, выложить релиз `python tools/release.py`, закоммитить
и запушить.

В отчёте владельцу — по жалобе на абзац: что было, в чём оказалась причина, что
изменилось. Список закрытых номеров без разбора бесполезен.
